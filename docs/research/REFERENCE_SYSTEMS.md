# Reference systems: source evidence and adoption decisions

Research snapshot: 2026-10-18. This is a bounded source review for an hours/days/weeks return-forecasting platform with data provenance, recovery and isolated Python ML. It is not a benchmark, an implementation plan to import all seven systems, or evidence of Scryntic forecast performance. Execution components are examined only as future design references; this research grants no trading authority.

All seven mandatory public repositories were read through the connected GitHub tools (`github_fetch` and `github_fetch_file`), pinned to the commit returned by the default-branch commits endpoint. Source files, relevant symbols and line ranges are linked below. Repository licences were read at those same commits. These are source observations and explicitly labelled engineering inferences; upstream tests/builds were not run, dependencies were not installed, and no live exchange connection or trading account was used. A source-level guard is not a demonstrated operational guarantee.

## Qlib: explicit data, processor and experiment boundaries

Source inspected:

- [`qlib/data/dataset/handler.py`, `DataHandlerLP.fit`, `_run_proc_l`, `process_data`](https://github.com/microsoft/qlib/blob/54355232463878d2eebb91fe0ee5fa7fa1f5976c/qlib/data/dataset/handler.py#L513-L609), blob `2c45aec687f02dd31132c64a0797c31458dde5cd`.
- [`qlib/workflow/recorder.py`, `MLflowRecorder.save_objects`, `load_object`, logging methods](https://github.com/microsoft/qlib/blob/54355232463878d2eebb91fe0ee5fa7fa1f5976c/qlib/workflow/recorder.py#L407-L504), blob `de023de842373df00671ae257b97a602df10cbff`.
- [`qlib/utils/mod.py`, `get_module_by_module_path`, `init_instance_by_config`](https://github.com/microsoft/qlib/blob/54355232463878d2eebb91fe0ee5fa7fa1f5976c/qlib/utils/mod.py#L50-L96), blob `8538913598eb47d7e898d8ed560b975aef6a3716`.

Observed: `DataHandlerLP` maintains shared, inference and learning processor lists and separate `_infer`/`_learn` frames. Inference processors must report `is_for_infer()`; processing may copy frames to avoid mutation. `fit()` itself passes the handler's `_data` to every processor, and `process_data(with_fit=True)` fits each stage on its current frame. Thus the split is a useful API pattern, but safe fitting intervals still depend on configured processors and datasets. Merely naming a frame “train” does not prove that normalization, feature construction or labels were causal.

Observed: `MLflowRecorder` separates parameter/metric/tag logging from artifact persistence. At this inspected revision, loading defaults to `RestrictedUnpickler`; unrestricted pickle requires explicit trust and warns about code execution. File-based plugin imports require an explicit top-level boolean trust flag; package imports still use `importlib.import_module`. The source explicitly states that this mechanism does not sandbox code or authorize artifact deserialization. These details are revision-specific and should not be assumed for old Qlib deployments.

Decision: adopt the *contracts* of a dataset version, separate fitted training processors, inference processors, model and recorder. An optional Qlib experiment may run only in an isolated worker against an exported immutable Scryntic dataset. Keep Scryntic's provenance and recovery authority outside Qlib; use explicit parent dataset hashes, event/availability cutoffs, feature/label definitions, fitting range, code/environment hash and output schema. Avoid importing arbitrary workflow configuration or pickle into the trusted service.

Cost and limits: medium adapter cost (time/instrument indexing, calendars, field naming, processor states and recorder IDs), plus Python/numerical dependencies and artifact storage. The pinned [`pyproject.toml`](https://github.com/microsoft/qlib/blob/54355232463878d2eebb91fe0ee5fa7fa1f5976c/pyproject.toml#L23-L76) declares Python `>=3.8.0` and optional Torch dependencies; an exact compatible environment and artifact-store configuration still need qualification. Qlib's research abstractions do not establish exchange ingestion recovery, Scryntic isolation, a durable job protocol, or return-forecast accuracy. MIT permits code reuse subject to notices; pretrained models and data require separate origin and licence records.

## Freqtrade/FreqAI: walk-forward mechanics with configurable leakage risks

Source inspected:

- [`freqtrade/freqai/data_kitchen.py`, `make_train_test_datasets`](https://github.com/freqtrade/freqtrade/blob/84e5657e698ec6ff279c6a4c04c7591dfefaec74/freqtrade/freqai/data_kitchen.py#L124-L199), `split_timerange`/`slice_dataframe` at [316–386](https://github.com/freqtrade/freqtrade/blob/84e5657e698ec6ff279c6a4c04c7591dfefaec74/freqtrade/freqai/data_kitchen.py#L316-L386), and `buffer_timerange` at [985–1005](https://github.com/freqtrade/freqtrade/blob/84e5657e698ec6ff279c6a4c04c7591dfefaec74/freqtrade/freqai/data_kitchen.py#L985-L1005), blob `8ef3e308216ecd1991ad68af397faaf5538461d9`.
- [`freqtrade/freqai/freqai_interface.py`, `IFreqaiModel.start_backtesting`](https://github.com/freqtrade/freqtrade/blob/84e5657e698ec6ff279c6a4c04c7591dfefaec74/freqtrade/freqai/freqai_interface.py#L272-L406), blob `8cc0497644c0540cec9ba5b586b36f2b0128c78d`.

Observed: training/backtest windows slide chronologically; the backtest begins at the training stop. Backtest slicing uses a half-open interval. Targets are recomputed on a frame truncated before each training/backtest stop; the training range can be buffered after indicators are populated. Training failure persists metadata and produces null predictions rather than treating an absent model as a valid predictor. These are useful lifecycle patterns.

Observed limitation: `make_train_test_datasets` defaults `shuffle=False` only when absent, then forwards user `data_split_parameters` to `train_test_split`. Configuration can change this; `shuffle_after_split` and `reverse_train_test_order` also exist. Indicators can be populated on the full input frame before slices. A noncausal custom indicator, cross-series merge, revised observation, or future-known covariate supplied incorrectly can therefore defeat a chronological outer loop. The buffer is configured in candles; it is not an automatic purge/embargo derived from every label's hours/days/weeks endpoint.

Decision: borrow walk-forward job structure, model-age/status metadata and explicit unavailable predictions. Do not adopt Freqtrade's trading bot runtime or its strategy callbacks as the forecasting service's authority. Scryntic must fix chronological splits in its own manifest, purge any training label whose complete outcome interval reaches validation/test, embargo overlapping folds as specified by the evaluation protocol, fit transformations only on training, and enforce availability-time joins. Compare labels/forecasts by horizon rather than one pooled bot metric.

Cost and limits: high cost to adopt the whole bot (exchange state, strategies, order lifecycle, configuration and UI outside the forecasting scope); much lower cost to re-express documented design ideas independently. The pinned [`pyproject.toml`](https://github.com/freqtrade/freqtrade/blob/84e5657e698ec6ff279c6a4c04c7591dfefaec74/pyproject.toml#L16-L104) requires Python `>=3.12` and separates optional ML dependencies; model backend and platform compatibility need their own lock/build check. GPL v3 is a material code-integration/distribution decision; do not copy implementation under an assumed permissive licence. User-trained model artifacts, strategy files and exchange data need separate licensing and provenance. No FreqAI backtest was run here.

## NautilusTrader: native domain logic and controlled simulation clocks

Source inspected:

- [`crates/model/src/orderbook/book.rs`, `OrderBook.apply_delta`, `apply_deltas`, `increment`](https://github.com/nautechsystems/nautilus_trader/blob/6875261266758e379d7af4213b327ea78fa8da01/crates/model/src/orderbook/book.rs#L295-L477), with high-water handling at [1170–1208](https://github.com/nautechsystems/nautilus_trader/blob/6875261266758e379d7af4213b327ea78fa8da01/crates/model/src/orderbook/book.rs#L1170-L1208), blob `ccd7ae44e9678f6311874a75b1f1d6d7fadac1cf`.

- [`crates/model/src/python/orderbook/book.rs`, PyO3 `impl OrderBook`](https://github.com/nautechsystems/nautilus_trader/blob/6875261266758e379d7af4213b327ea78fa8da01/crates/model/src/python/orderbook/book.rs#L16-L49), blob `095b1a7f41b92cab3923539f0e4c55f8e0acc8bf`; [`Cargo.toml`](https://github.com/nautechsystems/nautilus_trader/blob/6875261266758e379d7af4213b327ea78fa8da01/Cargo.toml#L1-L56), blob `bb907571e3100b210d7e3766e5281303bc18c71b`; [`python/pyproject.toml`](https://github.com/nautechsystems/nautilus_trader/blob/6875261266758e379d7af4213b327ea78fa8da01/python/pyproject.toml#L24-L46), blob `c7543493fa886bde8c137048d138ff01183ecbd2`.

Observed: the inspected architecture has distinct Rust crates for model, data, persistence, event store, backtest, execution, risk and adapters. `OrderBook` is implemented in Rust and exposed through PyO3; this is concrete native computation rather than a Python facade alone. Its checked entry point validates instrument identity. The source documents that “unchecked” skips that identity check to accommodate an FFI interning limitation; other validation remains. Sequence/time regressions in `increment` produce warnings and preserve metadata high-water marks. This is **not** proof that every stale or missing update is rejected before state mutation; an exchange-specific continuity contract is still needed.

Observed: the backtest loop advances clocks using each item's `ts_init`, routes data to the simulated venue and data engine, and handles timers and shutdown. Reset orders exchange reset before execution-cache reset. Canonical results explicitly remove host/process/random identity and wall-clock noise while retaining domain state. These are useful references for specifying what deterministic comparison should include and exclude. A virtual-clock backtest and an in-memory reset do not establish crash recovery, exactly-once external effects, or equivalence to a live venue.

Decision: preserve a future boundary between deterministic domain state/replay and Python model execution. Consider Rust/native work only for measured CPU/latency bottlenecks or a separately justified durable domain component. First define the event schema, sequence/epoch semantics, replay ordering, snapshot format and cross-language conformance fixtures. Native memory safety does not remove FFI, dependency, input-validation or worker-authority concerns. An optional future Nautilus simulation service must consume immutable exported data and return observations; it must not receive production order authority by inheritance.

Cost and limits: high adoption cost for the whole engine (domain/calendar/instrument mapping, clocks, numeric types, fills, events and operational deployment). The inspected workspace declares version `0.67.0`, Rust `1.99.0`, and LGPL-3.0-only; the Python package uses Maturin `1.15.0` and requires Python `>=3.13,<3.15`. These are the pinned tree's declarations, not a tested Scryntic build recipe. Wheels/ABI, Rust toolchain, native linking, serialization compatibility and LGPL obligations must be qualified independently. No pretrained weight artifact is part of the examined order-book/backtest path.

## cryptofeed: snapshot/delta synchronization, with publication-order caveats

Source inspected:

- [`cryptofeed/exchanges/binance.py`, `Binance._check_update_id`, `_bridges`, `_book`](https://github.com/bmoscon/cryptofeed/blob/ad986f01743ddbb81f65981ecf4946c8d629520e/cryptofeed/exchanges/binance.py#L332-L449), blob `076f9bf6fdddf7eb9cb0e4df7b4d07c57a57a3e9`.
- [`cryptofeed/util/snapshots.py`, `SnapshotSync._buffer_update`, `_fetch_snapshot`, `_install_snapshots`](https://github.com/bmoscon/cryptofeed/blob/ad986f01743ddbb81f65981ecf4946c8d629520e/cryptofeed/util/snapshots.py#L31-L152), blob `5dd92537106f7da6517361d7d2e9ba13c9b238b5`.
- [`cryptofeed/feed.py`, `Feed.book_callback`, `check_bid_ask_overlapping`](https://github.com/bmoscon/cryptofeed/blob/ad986f01743ddbb81f65981ecf4946c8d629520e/cryptofeed/feed.py#L477-L512), blob `1cf666b674a44622e0327bb8933ca2b75cb03574`.

Observed: the Binance path buffers deltas until a snapshot arrives, discards deltas covered by the snapshot, verifies a bridge to the next update, ignores covered old updates and drops a live book on a sequence gap. The synchronization helper binds pending work to a connection identity, limits buffered updates, restarts on overflow/stale snapshots and applies buffered deltas after installing a snapshot. This gives specific recovery states to emulate: unsynchronized, buffering, snapshot candidate, bridged and live. The examined helper's defaults include 2,000 buffered updates and snapshot concurrency five; these are implementation settings, not sizing recommendations.

Observed limitation: checksum support is venue-dependent. `Feed.book_callback` attaches raw data, timestamps, sequence, checksum and delta, then invokes downstream callbacks **before** raising its sustained crossed-book exception. Therefore a callback consumer may already have observed an invalid/crossed book; enabling an upstream check is not sufficient to prove that all persisted or feature-consumed records were validated first. Some venues explicitly tolerate crossed books, and source defaults/exception policy depend on venue capability. The Binance example is not evidence that every connector has the same continuity semantics.

Decision: use the snapshot-bridge and bounded-buffer patterns. Every ingested book-derived feature must carry venue/instrument, connection and book epoch, snapshot/delta sequence, event/receipt/availability timestamps, raw-parent hashes, validation result and gap/reset reason. On a gap, overflow or failed checksum, mark the epoch unusable for feature publication until a venue-correct resynchronization succeeds. Retain raw evidence and distinguish unusable intervals from zero activity. This consumer contract must be independently tested with duplicate, missing, reordered and reconnect-crossing deltas.

Cost and limits: medium-to-high adapter/operations cost (venue semantics, REST snapshot rate limits, websocket lifecycle, backpressure, storage volume and book invalidation). The pinned [`pyproject.toml`](https://github.com/bmoscon/cryptofeed/blob/ad986f01743ddbb81f65981ecf4946c8d629520e/pyproject.toml#L7-L49) requires Python `>=3.13` and Cython build tooling. The current licence is **AGPL v3 or later**, including a network-use consideration for modified covered software; this review does not qualify an adoption/licensing arrangement. Keep it as a source reference unless that decision is made explicitly. Exchange data rights remain independent. No ML weights are involved in the examined ingestion path.

Observed: exchange-specific code translates raw Binance `U`/`u` identifiers into `first_update_id`/`update_id`; the data source handles transport/subscriptions/snapshots, while the generic tracker routes messages to per-pair queues, saves early messages and maintains a bounded past-diff window. Apache 2.0 code licensing does not confer market-data redistribution rights. No forecasting weights were inspected in this path.

## NeuralForecast: multi-horizon losses and explicit calibration interfaces

Source inspected:

- [`neuralforecast/core.py`, `NeuralForecast.fit`, `cross_validation`, `_conformity_scores`](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/neuralforecast/core.py#L948-L971), cross-validation at [2439–2664](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/neuralforecast/core.py#L2439-L2664) and calibration scores at [3111–3168](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/neuralforecast/core.py#L3111-L3168), blob `894d9406c156a3ee857d2cfa77211b31ed863e00`.
- [`neuralforecast/losses/pytorch.py`, `MQLoss`, horizon weighting and pinball aggregation](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/neuralforecast/losses/pytorch.py#L640-L768), blob `de1b3c472c68bb6ece2c8b9754cb07efb4704634`.
- [`neuralforecast/utils.py`, `PredictionIntervals`, conformal distribution/error interval methods](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/neuralforecast/utils.py#L479-L663), blob `8fefcc38ad7f375a6bbd776946973821c4310c10`.

Observed: models share a configured horizon; cross-validation exposes cutoff, number/step of windows, validation/test size and refitting. Calibration retrains via cross-validation; this revision rejects the incompatible combination of fitted-model reuse and prediction intervals, and interval-enabled cross-validation requires refitting. `MQLoss` computes quantile losses with masks and optional per-horizon weighting. The interval helper reshapes conformity scores by series, window and horizon before computing quantiles. These are concrete components for a multi-horizon evaluation adapter.

Observed limitation: accepting two calibration windows is an API minimum, not a statistical argument that market-return intervals are reliable. Masking and weighted aggregation can conceal weak long-horizon performance if only one scalar is reported. Conformal interfaces do not themselves establish exchangeability under drift, point-in-time features, correct corporate-action/funding treatment, leakage-free label construction, or out-of-domain calibration.

Decision: a candidate for train-from-scratch challengers inside isolated Python workers. Use Scryntic-owned immutable training/calibration/test manifests and report each requested hours/days/weeks horizon separately. Record the exact target (for example terminal log return from the decision-time price), frequency/calendar, missingness mask, model/loss/horizon weights, scaler fit range, random seed, refit policy, calibration sample size and evaluation cutoff. Score point forecasts and pinball/CRPS-style distribution quality where the forecast representation supports it; measure empirical interval coverage, width, quantile crossing and conditional failures by horizon, asset, volatility and time regime. Calibration and model selection must finish before the untouched test period.

Cost and limits: medium worker-adapter cost and potentially substantial training/search/calibration cost. The inspected [`pyproject.toml`](https://github.com/Nixtla/neuralforecast/blob/6c11accfbcfdd62a40ef69a7c81e3d9c7f272682/pyproject.toml#L14-L38) requires Python `>=3.10`, Torch `>=2.9.1` and PyTorch Lightning `>=2.6.6`; exact locked versions/hardware still need qualification. Apache 2.0 applies to this code, not automatically to third-party pretrained checkpoints. Prefer an initial owned-data baseline so the training corpus is auditable. No NeuralForecast model was trained or evaluated in this review.

## Cross-system conclusions and admission requirements

These decisions are engineering inferences from the inspected boundaries; they are not claims that the integration already exists.

| Boundary | Reuse/reference decision | Acceptance evidence before adoption |
|---|---|---|
| Public ingestion and book state | cryptofeed/Hummingbot patterns; no whole-bot import | Venue-specific snapshot bridge/checksum rules; raw replay; duplicate/gap/reorder/reconnect/overflow fixtures; explicit invalid epochs and data rights |
| Dataset and experiment orchestration | Qlib-style data/processor/model/recorder contracts | Immutable parent hashes; as-of availability joins; label endpoints; train-only fitted transforms; split/purge manifests; idempotent artifact publication |
| Python modelling | NeuralForecast owned-data baselines; Chronos optional challenger | Isolated workers; locked environments; explicit typed input/output; resource/timeout limits; parent-controlled job state; model/corpus licences; reproducible forecast origin |
| Native domain/replay | Nautilus Rust and virtual-clock reference | Profiling-based need; deterministic schema/order/numeric contracts; cross-language conformance; snapshot/restart evidence; ABI/toolchain qualification |
| Future trading | Separate future design only | Independent authorization and design for credentials, risk, order idempotency, reconciliation and kill controls; forecast success does not enable execution |

For hours/days/weeks forecasts, define horizons by duration and calendar explicitly; a library's `h` is a count of observations. Freeze the observation frequency, origin price, terminal target time, publication/availability cutoff, revisions policy and stale-data policy. Preserve fees/funding/slippage assumptions separately if any later economic evaluation is performed. Forecast quality, hypothetical utility and executable trading safety are different claims.

Recovery must be specified at the Scryntic boundary: an immutable dataset/model/run identity, append-only attempts, durable checkpoint/artifact hashes, resumable input position, explicit failed/unavailable states, and atomic promotion of a complete output. Upstream model/recorder/book abstractions do not by themselves prove recovery across worker kill, host crash, partial file write, duplicate completion or stale result delivery. Validate these cases independently when implementation is authorized.

Evaluation admission requires chronological train/calibration/test and prospective periods, label-overlap purging, train-only transformations, baselines, horizon-specific uncertainty and coverage checks, and a recorded family of model-selection trials. Use block-aware uncertainty estimates appropriate to serially dependent/overlapping returns; report sample sizes and regime variation. Stop promoting a model when required provenance, data validity, calibration or operational evidence is absent. This is an acceptance design, not a claim that any candidate has passed it.
