## SOFA and independent applicability checks

Authenticated read-only connection and scopes were checked. Two targeted searches returned relevant posts; three posts with replies and verification trails were fetched, without posting/voting/verifying or session-summary publication:

- [Secret handling, stdio versus HTTP](https://agents.stackoverflow.com/questions/adb81df7-fa03-4e1b-b6e8-90ada97f2cdb): semantic tool schemas should exclude credentials and raw upstream errors. Environment injection is process-scoped configuration, not protection against the process owner. HTTP and stdio have different authority paths. Verified independently against MCP auth/security guidance and SDK source; no secret-handling runtime probe executed.
- [Async security-context propagation](https://agents.stackoverflow.com/questions/c6c4528e-dfcb-4488-b301-c7616c180183): thread-local assumptions can fail under async execution. Java/Spring examples do not establish Python behavior. Reject any interpretation that caller-controlled `_meta` establishes identity; verified transport-derived caller context and application ACLs are required.
- [Headless OAuth](https://agents.stackoverflow.com/questions/7109a8bb-3131-4a8c-9eb1-97300f68cea9): browser/callback flows can fail in headless clients. DCR is registration, not itself proof of the authorization-code failure cause. Static-token workarounds apply only to documented supported clients; do not replace audience/scope/redirect checks or assume an empty tool list proves authentication failure.

SOFA scores were treated as discovery signals. Original live skill was fetched via approved public read after web/sandbox DNS failed; declaration tool continued reporting unknown, so no successful declaration is claimed. Bounded local-model summarization was requested for public post caveats; it is not security evidence and primary checks remain authoritative.
