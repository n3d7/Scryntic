# Engineering evidence and security decisions

Reviewed: 2026-10-18. Repository baseline: `8e1465fd389e440763ef69b7c59832ad2f8bd8de`.
Status: proposed architecture and research record. No dependency, runtime, worker service or trading capability is delivered by this document. See [the scoped threat model](../architecture/THREAT_MODEL.md).

## Recommended direction

Keep a modular Python control plane and preserve the existing durable job, provenance and artifact contracts. Run native analytics and models in separately admitted processes with immutable inputs and bounded primitive outputs. Introduce Rust only for a measured bottleneck with a small stable interface. Begin with reproducible hourly, daily and weekly forecast experiments before increasing model or infrastructure complexity. There is no engineering evidence here for a repository rewrite, Kubernetes or an automatic move from forecasting to trading.

The proposed compute pool accepts any operator-enrolled host that meets the selected task profile. Eligibility belongs to a host/profile/runtime combination with fresh qualification evidence; it is not implied by an operating-system name, a GPU advertisement or a successful heartbeat. A host may be eligible for a bounded CPU feature task and ineligible for a GPU model task. Remote pull leases and a host agent are proposed additions, not an existing distributed service.

## Compute admission, execution and result acceptance

The proposed coordinator owns task admission, immutable manifests, budget reservation, scheduling policy, leases, cancellation, result validation and final acceptance. A trusted host agent alone holds its narrow enrollment/transport credential and launches approved profiles. The model/analytics process receives no transport credential, exchange credential, credential reference or network access. The host agent's authenticated transport and the worker's offline execution are distinct boundaries.

Each immutable task manifest binds at least:

- task kind/schema, run/task identifiers, input object digests and sizes, provenance/availability cutoff, feature/label/split versions and all required parameters;
- code/adapter revision, model weights/config/preprocessor digests, runtime dependency inventory and isolation profile digest;
- stable task/replicate seed, dtype/device/determinism policy, native thread budget and required host capabilities;
- admitted CPU, memory, scratch, output, process, wall-time and optional GPU/VRAM budgets; permitted output schema and metric protocol.

Jobs do not supply shell fragments, Python import strings, unreviewed SQL, executable paths, URLs to download, arbitrary mounts or systemd properties. Budget changes create a new manifest/admission decision. Preprocessing, feature engineering, fitting, inference and scoring have separate task types and data scopes. Fitting may see only its admitted training portion; inference receives only features available at its forecast origin; held-out labels remain with the scorer where practical.

Workers pull bounded batches from the coordinator. Claim and renewal are conditional transactions against authoritative coordinator state; they never depend on worker wall time. Expiry transitions and the next attempt/history record are explicit. Every issued attempt has a monotonically advancing fencing value and an unguessable scoped token bound to the task manifest, enrolled host and attempt. Renewals, cancellation and returned results must carry that exact identity. Restart requires recovery and invalidation of prior ownership before reissue; ambiguity fails closed. A partitioned worker may keep computing, but cannot revive its authority by sending a late heartbeat.

Promise at-least-once dispatch with at-most-once accepted outcome for a logical task, not exactly-once physical execution. Acceptance rechecks manifest, current fencing/token/host, cancellation/deadline/revocation, allowed schema, finite bounds, output sizes/digests and expected rows/timestamps. Duplicate identical submissions return the existing receipt; conflicting duplicates are rejected and recorded. Artifact installation and durable success need an explicit crash-recovery protocol preserving the existing no-overwrite semantics. Neither an uploaded artifact nor a zero exit code alone is accepted success.

A host can lie about execution or return plausible fabricated numbers. Hashes identify bytes, signatures authenticate the enrolled sender and bootstrap observations describe a particular local execution; none proves honest computation. Use protected deterministic canaries, coordinator-side score recomputation, selected independent reruns and anomaly/quarantine policy for valuable results. Redundant execution detects some disagreement; colluding or uniformly compromised workers remain outside that guarantee. Data confidential to the operator must not be sent to hosts whose administrators are untrusted.

GPU tasks require a distinct profile and host qualification covering driver/runtime/device access, VRAM/OOM behavior, process cleanup and device-state retention, concurrency, shared-memory/device-node exposure and reproducibility tolerance. Do not weaken the CPU profile or infer GPU eligibility from successful CUDA initialization. Dedicated hosts or stronger VM boundaries may be necessary for the selected threat model; this document does not claim containers or GPU partitioning provide certified containment.

## Forecast evaluation and reproducibility contract

Use calendar/availability-based rolling origins and explicit hourly/daily/weekly target definitions. Keep train, tuning and final evaluation separate; fit scalers, selection, imputers and learned representations only on the training information permitted at each origin. Include a policy for overlapping label windows and any purge/gap derived from their actual horizon. Date ordering alone cannot fix revised data or late availability: manifest both event time and knowledge/availability time.

Every experiment retains the original admissible universe, exclusions and failures, target unit/transformation, label-close semantics, origin/cutoffs, baseline predictions, seeds and metric code. Compare against persistence/zero-return and horizon-appropriate simple baselines on the same eligible observations. Predeclare tolerances and improvement margins before reading the final holdout. Record point accuracy and uncertainty/calibration where offered. Core research includes preregistered cost-sensitivity diagnostics for fees, spread, funding and slippage. Detailed fill simulation, account risk controls and execution belong to the later separate trading program; these diagnostics confer no trading authority.

Distinguish three reproducibility levels: identical bytes for manifests and admitted primitive artifacts; repeatability within a pinned runtime/profile with stated numeric tolerances; scientific robustness across periods, assets, seeds and eligible hardware. None implies the next. Preserve failed/deferred tasks as outcomes, and report actual resource measurements separately from configured limits.

## Decisions to carry into implementation planning

1. Preserve the Python control plane and Foundation evidence; reconcile stale security/worker prose without erasing dated qualification history.
2. Specify and test manifests, capabilities, crash recovery, lease expiry/fencing and idempotent acceptance before distributing jobs.
3. Qualify a CPU analytics task profile first; benchmark DuckDB/Polars against the current path only after selecting immutable workloads. Rust needs a measured candidate, a pinned compatibility matrix and explicit FFI ownership/error semantics.
4. Add GPU only as a separately admitted task/host profile after CPU correctness and recovery are established.
5. Promote research to host qualification, then production operations, through separate evidence gates. Forecast success does not authorize financial execution.
